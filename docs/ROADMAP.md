## E1 - Rollback / version history
CLI: before replacing an addon, copy the previously installed zip (the one that produced the current fileId) into `ROOT\backups\<projectId>\<fileId>.zip`; simplest implementation: after every successful install keep the downloaded zip there (move it from staging instead of deleting) and prune so at most 2 zips per project remain (newest two). Record gains `previousFileId` (int64|null) and `previousVersion` (string|null) set on every update (the fileId/version being replaced). New param `-Rollback <int[]>`: for each id, if `backups\<projectId>\<previousFileId>.zip` exists install from that local zip (same Install-AddonPackage path, no download), swap fileId/version with previous, set `pinnedFileId` to the restored fileId (so it is not immediately re-updated), status row `Rolled-back`; else `Failed` with reason. `-Json` supported.
Server: job kind `rollback` `{projectId}` -> `-Rollback id`. `/api/state` records expose previousFileId/previousVersion.
UI: kebab "Roll back to <previousVersion>" (only when previousFileId present); Versions tab marks the previous file "Previous"; after rollback the row shows Pinned with a tooltip "Rolled back - unpin to resume updates".
ACCEPTANCE: install 911525 at an older fileId via -FileId, unpin, sync to newest -> backups has both zips, record.previousFileId = older; -Rollback 911525 -> record.fileId = older, pinnedFileId = older, folder contents match the older version (toc Version line), status Rolled-back; prune: never more than 2 zips per project.

## E12 - Wago Addons as a second source (keyless) - REQUESTED BY ERIC, TOP PRIORITY
Goal: update and manage addons hosted on addons.wago.io exactly like CurseForge ones - install, update, pin/ignore/rollback, versions with changelogs, browse/search - with no API key. Everything below is VERIFIED on this machine on 2026-09-02 (builders: copy this block into SPEC.md as "## Wago Addons access facts (verified)").

Wago website facts (send the same browser User-Agent as for CurseForge; pace >= 300 ms; on HTTP 429/503 wait 5 s and retry once; never use the official /api/external/* endpoints - they need a paid key):
- Inertia handshake: `GET https://addons.wago.io/addons/{slug}` (plain, Accept text/html) -> 200 HTML; the `<div id="app" data-page="...">` attribute (HTML-entity-encoded JSON) has `version` (e.g. a1c7e58fc4a75de82b84b6c240869fd9), `component`, `props`, `url`. Send `X-Inertia: true`, `X-Inertia-Version: <version>`, `X-Requested-With: XMLHttpRequest`, `Accept: text/html, application/xhtml+xml` on any page URL to get that page's props as pure JSON (200, application/json). A 409 means the version changed: re-read it from the HTML page and retry once. Cache the version in state.json.
- Addon details: `/addons/{slug}` JSON -> `props.addon` = {id (string like "ZKbxbRN1" = the `## X-Wago-ID` in .toc files), slug, display_name, summary, thumbnail_image (cdn url), categories[{id, display_name, icon}], website, source_url, support_url, discord_url, is_unlisted}, `props.description` (plain text/markdown), `props.metadata` = {last_update, download_count, like_count, developers[{name, avatar}], owner, recent_releases{retail{label, changelog,...}, ...}}.
- Releases: `/addons/{slug}/versions?page=N` JSON -> `props.releases` is a Laravel paginator {data[], current_page, last_page, per_page (10), total, next_page_url}; each release = {id (string like "r6p5g7zQ"), addon_id (int), size (bytes), label (version text), stability ("stable"|"beta"|"alpha"), changelog (markdown), created_at (ISO), supported_retail_patches[] (e.g. "12.1.0"), supported_classic_patches[], supported_mop_patches[], ..., download_link (signed URL `https://addons.wago.io/download/{id}?expires=&link=&signature=`, valid ~24 h)}. Possibly filterable with `?stability=`.
- Download: GET the signed download_link with redirects allowed -> 302 -> `https://cdn.wago.io/public/addons/{addonId}/{hash}/{name}.zip` (200, application/zip, Content-Length == release.size). Verify size. `/download?addonId={id}` is only an HTML landing page - do not use it.
- Search/browse: `GET https://addons.wago.io/?search={q}&game_version=retail[&category={categoryId}][&page=N]` JSON -> `props.addons` paginator (15/page) whose `data[]` items are server-rendered HTML CARD SNIPPETS, not objects: parse each with regexes for `href="https://addons.wago.io/addons/([a-z0-9-]+)"` (slug), the `<h3 ...>NAME</h3>` (display name), `src=(https://cdn.wago.io/thumbnails/...)` (thumbnail) and any summary/author/download-count text present; `props.allCategories` = [{id, display_name}] (29 entries); `props.sort` echoes a sort param (test values such as popular, updated, downloads, name and document which work). Full details for a card come from `/addons/{slug}`.
- Gallery/screenshots: `/addons/{slug}/gallery` JSON (props contain image URLs - inspect and document).

CLI (addon-sync.ps1): records gain `source` ("curseforge" default, or "wago"), `wagoId` (string), `slug` (string), and for cross-source awareness `curseId` (from `## X-Curse-Project-ID`) and `wagoId` are parsed from the primary .toc at every install regardless of source. For Wago records fileId is the release id STRING (e.g. "r6p5g7zQ"), version = label, fileName = zip name. `-Add` becomes `[string[]]`: numeric -> CurseForge project id; `wago:<slug>`, `wago:<id>`, or `https://addons.wago.io/addons/<slug>` -> Wago (resolve ids to slug via the addon page: if given an id, use `/addons/{id}` - test whether the site accepts ids in place of slugs; otherwise require slug). `-FileId` accepts a release id string for Wago. `-Files` lists Wago releases (label, stability, date, size, retail patches, changelog present yes/no). Release selection: newest release whose stability is allowed by releaseType (1 stable, 2 stable+beta, 3 all) and whose supported_retail_patches is non-empty (fallback: newest allowed stability). Pinned/ignored/rollback/dependencies/backups behave identically. `-Scan` also reports `wagoId`/`curseId` found in each untracked folder's .toc so the UI can offer one-click adoption from either source. All existing CurseForge behaviour unchanged; -Json shapes gain the new fields.
Server: `GET /api/wago/search?q=&categoryId=&sort=&page=` -> {items:[{slug, wagoId?, name, thumbnail, summary?, author?}], page, lastPage, total}; `GET /api/wago/categories`; `GET /api/wago/addons/{slug}` -> details + metadata + description; `GET /api/wago/addons/{slug}/releases?page=` ; `GET /api/wago/addons/{slug}/gallery`; `GET /api/wago/resolve?url=` -> {slug}. 5-minute cache. Job kinds add/install accept `{source:"wago", slug, fileId?}` and map to the CLI forms above. `/api/state` exposes source/wagoId/curseId per record.
UI: Browse gets a source switch (CurseForge | Wago Addons); Wago browse works with no key (search, category select from allCategories, pagination); cards open the detail drawer: Overview (summary, description, developers, downloads, likes, categories, links), Versions (releases with stability badges, retail patches, size; Install per row), Changelog (per release, markdown rendered safely - a minimal markdown-to-HTML converter for headings/bold/lists/links is fine, sanitized), Screenshots (gallery). ## E13 - Compatibility audit in the app (Midnight / current patch validity)
Goal: make "is every addon valid for the current patch and season" a permanent, visible signal instead of a manual audit. Game context: Midnight (12.x); Season 2 runs on 12.1.0; the client build is in `<WoW>\.build.info` (pipe-separated, header row has `Version` and `Product`; the `wow` row's Version is e.g. 12.1.0.69587 -> Interface number 120100 = major*10000 + minor*100 + patch).
CLI: `-Status -Json` and every sync/check result gain per record: `tocInterfaces` (int[] parsed from the primary .toc `## Interface:` line, comma/space separated; also honour `## Interface-Mainline:`), `latestGameVersions` (string[] from the newest selected CurseForge/Wago file, captured at check/sync time and stored on the record as `latestGameVersions` + `latestFileDate`), and `clientBuild`/`clientInterface` (top-level in the JSON, read from .build.info once per run; cache in state). Compute `compat` per record: `ok` (toc has clientInterface OR latestGameVersions contains client major.minor.patch), `stale-minor` (supports same major but older minor, e.g. 12.0.x only), `stale` (nothing for the current major), `unknown`.
Server: `/api/state` exposes clientBuild/clientInterface and per-record compat fields; `/api/diagnostics` includes the client build.
UI: My Addons gains a "Compatibility" column (chip: Built for 12.1 / Older patch (12.0.7) / Not for Midnight) with tooltip listing toc Interfaces and the newest file's game versions + date; a filter chip "Stale" with count; the header shows "Client 12.1.0.69587 - N addons need attention". Drawer Overview shows the same detail. WoW's `checkAddonVersion` cvar (WTF\Config.wtf, `SET checkAddonVersion "0"` = load out-of-date addons) is displayed in Settings > Game as read-only info with an explanation.
ACCEPTANCE: with a scratch AddOns dir containing one addon whose toc says 120007 only, -Status -Json reports compat stale-minor; the UI shows the chip and the Stale filter counts it; an addon with 120100 shows Built for 12.1; the client build line renders from a copied .build.info (the test must not read the real WoW folder - allow a `-BuildInfoPath` override on the CLI and server for tests).
