## CurseForge access facts (verified)

Keyless "website" endpoints that WORK from scripts (send `User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/128.0 Safari/537.36`, `Accept: application/json`, `Referer: https://www.curseforge.com/`; keep >= 300 ms between requests; 403/429 -> wait 5 s, retry once):
- `GET https://www.curseforge.com/api/v1/mods/{projectId}/files?pageIndex=0&pageSize=20&sort=dateCreated&sortDescending=true&removeAlphas=true` -> `{data:[file...], pagination}` newest first. file = `{id, dateCreated, displayName, fileName, fileLength, gameVersions[], gameVersionTypeIds[], releaseType, status, totalDownloads, user:{username, id, twitchAvatarUrl}}`. 517 in gameVersionTypeIds = Retail. releaseType 1 release, 2 beta, 3 alpha. (Note `removeAlphas=true` must be dropped when the caller wants alphas.)
- `GET https://www.curseforge.com/api/v1/mods/{projectId}/files/{fileId}` -> `{data: file}` (same shape).
- `GET https://www.curseforge.com/api/v1/mods/{projectId}/files/{fileId}/download` -> 302 to CDN zip.
Keyless endpoints that are Cloudflare-BLOCKED (403): search, `mods/{id}`, description, changelog, all HTML pages. Never try to work around that.

Official CurseForge Core API - REMOVED ENTIRELY as of 2026-09-04 (Expansion E23, at Eric's explicit request: "I want the curse api key cleared, I want that removed as a feature"). This section originally documented it here as an OPTIONAL layer (header `x-api-key: <key>`, base `https://api.curseforge.com`, `/v1/games/1` key test, `/v1/categories`, `/v1/mods/search`, `/v1/mods/{id}` (+ batch `POST /v1/mods`), `/v1/mods/{id}/description`, `/v1/mods/{id}/files`, `/v1/mods/{id}/files/{fileId}/changelog`) - kept here, struck through in spirit, only so a future audit can see what was deliberately deleted and why, not as a contract anything in this app still honors. No code path in this app sends a request to `api.curseforge.com` any more, with or without a key; see E23 for the full removal.
Downloads ALWAYS go through the keyless website download endpoint (works regardless of allowModDistribution).

## addons.json record (ROOT\addons.json)

Existing fields: `name, projectId, fileId, version, fileName, installedAt, folders[]`.
New OPTIONAL fields (absent on old records - readers must tolerate absence; writers add them when touched): `author` (string|null, from file.user.username), `ignoreUpdates` (bool), `pinnedFileId` (int64|null), `releaseType` (int|null, per-addon override of settings.releaseType). When creating/updating a record always write all of these keys (null/false when unknown) so later dot-assignment never hits a missing property.

## 1. addon-sync.ps1 - required extensions (keep everything that exists)

Existing params stay: `-AddonsPath, -Add <int[]>, -Remove <string[]>, -Status, -Force, -DryRun, -Quiet`.
New params:
- `-Only <int[]>` : restrict the sync (or -Force reinstall) to these project ids.
- `-FileId <int64>` : requires exactly one id in `-Only` or `-Add`; install that specific file id instead of the newest, then set `pinnedFileId` = that id. Use `GET .../files/{fileId}` to get the file record (validate it belongs to the project; else Failed).
- `-Unpin <int[]>` : clear pinnedFileId on those records (no network), status row `Unpinned`.
- `-Ignore <int[]>` / `-Unignore <int[]>` : set/clear ignoreUpdates (no network), rows `Ignored` / `Unignored`.
- `-Files <int>` : list available files for that project (website endpoint, WITHOUT removeAlphas so all channels show, pageSize=20), no install, no config change. With -Json prints `{"action":"files","projectId":N,"files":[{id, displayName, version, fileName, dateCreated, releaseType, gameVersions[], fileLength, downloads, author, retail:bool}]}`; without -Json prints a table.
- `-Scan` : list top-level AddOns folders not owned by any record. For each: `{folder, title (## Title from <folder>.toc, color codes stripped, null if none), version (## Version), hasToc}`. Group nothing; one row per folder. -Json: `{"action":"scan","untracked":[...]}`.
- `-Json` : machine-readable mode. Print EXACTLY ONE JSON document to stdout and nothing else (no tables, no Write-Host noise; Write-Host is fine only when not -Json). Shape: `{"action":"sync|check|add|remove|status|files|scan|flags","results":[{"status","name","version","projectId","fileId"}],"addons":[full records] }` - `addons` is always included (current config after the operation) except for files/scan; `-DryRun` reports action "check". Status values: `Up-to-date, Updated, Installed, Removed, Failed, Skipped, Would-update, Ignored, Pinned, Unpinned, Unignored`.
- `-Launcher` : launcher mode; read settings.json; if `autoUpdateOnLaunch` is false, log INFO "auto-update disabled" and exit 0 without network. Otherwise behave like a normal sync.
Behaviour changes:
- Read settings.json for the default max releaseType. `Select-CfFile` takes `-MaxReleaseType`; selection = first file with 517 and releaseType <= max; fallback 517 any; fallback gameVersions startswith "12."; else none. Per-record `releaseType` overrides the setting when non-null. The list request must omit `removeAlphas=true` when max is 3.
- Records with `ignoreUpdates` true are reported `Ignored` and never touched during a plain sync; `-Force` or `-Only` including them still updates them (explicit intent).
- Records with `pinnedFileId` sync to that exact file (report `Pinned` when it already matches, `Updated` when it had to install it). `-Force` reinstalls the pinned file, not the newest.
- On every install/update also store `author` from the selected file's `user.username`.
- `-Add` may be combined with `-FileId` (single id).
- `-Status` (non-Json) table gains columns Author, Pinned, Ignored.
- Exit codes unchanged: 0 for operations, 2 for unusable config/path.
Everything else (pacing, retries, validation, atomic swap, stale cleanup scoped to the record's previous folders, logging, last-run.txt, staging cleanup) stays exactly as is.

## 2. addon-server.ps1 - local HTTP server

Params: `-Port <int>` (default settings.port or 47831), `-Root <path>` (directory holding addon-sync.ps1, addons.json, settings.json, ui\; default `$PSScriptRoot`), `-AddonsPath <path>` (override forwarded to every CLI call; default: the CLI's own auto-detection), `-IdleMinutes <int>` (default 20; exit when no request arrived for that long), `-OpenBrowser` (after start, launch Edge: `msedge.exe --app=http://localhost:<port>/ --window-size=1320,900`; if Edge missing use `Start-Process http://localhost:<port>/`).
Listener prefix `http://localhost:<port>/` only (never `+` or `*`). Single-threaded request loop; every handler must be wrapped in try/catch returning JSON `{error: "..."}` with 500 on unexpected failure; never let one request kill the server. Log to `ROOT\server.log` (timestamped, one line per request: method path status ms, plus errors). Respond `Cache-Control: no-store` for /api/. Content-Type `application/json; charset=utf-8` for API, proper MIME for static (html, css, js, svg, png, ico, woff2, json). Request bodies are UTF-8 JSON.
Static: `GET /` and `GET /index.html` -> ui\index.html; `GET /<file>` -> ui\<file> (reject any path containing `..` or a drive/absolute path; 404 if missing).

Jobs: long operations run the CLI as a hidden child process:
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<ROOT>\addon-sync.ps1" <args> -Json [-AddonsPath "<override>"]` with `Start-Process -PassThru -WindowStyle Hidden -RedirectStandardOutput "<ROOT>\jobs\<jobId>.out" -RedirectStandardError "<ROOT>\jobs\<jobId>.err"`. One job at a time (409 `{error:"busy", jobId}` if one is running). jobId = incrementing integer or short random hex. Record `sync.log` length at job start; the job's `log` = new lines appended since then (read each time /api/jobs/{id} is polled; tolerate the file being written concurrently by opening with FileShare ReadWrite). When the process exits: parse `<jobId>.out` as JSON -> `results`; state `done` (exit 0) or `failed` (non-zero or unparseable, include stderr text in `error`). Keep the last 20 jobs in memory. Delete job files older than 1 day at startup.
Job kinds and CLI mapping:
- `sync` `{ids?:[int], force?:bool}` -> `[-Only ids] [-Force]`
- `check` -> `-DryRun`
- `add` `{projectId:int, fileId?:int64}` -> `-Add id [-FileId f]`
- `remove` `{projectId:int}` -> `-Remove id`
- `install` `{projectId:int, fileId:int64}` -> `-Only id -FileId f`
- `launch` `{updateFirst:bool}` -> if updateFirst run a full sync job first, then (or immediately) `Start-Process "C:\Program Files (x86)\Battle.net\Battle.net.exe" -ArgumentList '--exec="launch WoW"'`; results row `{status:"Launched", name:"World of Warcraft"}`.
Fast (synchronous) operations run the CLI inline and wait: `-Ignore/-Unignore/-Unpin/-Status/-Files/-Scan` (all -Json). Timeout 60 s.

API (all JSON):
- `GET /api/state` -> `{ addons:[record + {updateAvailable: {fileId, version}|null}], settings:{releaseType, autoUpdateOnLaunch, port, hasApiKey, apiKeyHint (last 4 chars or ""), addonsPath, wowRoot}, lastRun:{timestamp, summary, rows:[{status,name,version}]}|null, job: <current or most recent JobStatus>|null, updatesCheckedAt: iso|null }`. `updateAvailable` comes from the most recent `check` job results kept in memory (Would-update rows keyed by projectId); a completed `sync` clears entries for addons that were updated. (Later expansions add more top-level fields not reflected in this original line - `clientBuild`/`clientInterface` per E13, `source`/`wagoId`/`slug`/`curseId` per record per E12, `freshness`/`lastCheckFailed`/`lastCheckError` per E20, and `job` itself gains a `progress` field per E20 - see each section for its own contract.)

- `GET /api/jobs` -> last 20.
- `POST /api/addons/{projectId}/ignore` body `{ignore:bool}` -> `{addons}` after change.
- `POST /api/addons/{projectId}/unpin` -> `{addons}`.
- `GET /api/addons/{projectId}/files` -> the CLI `-Files` JSON.
- `GET /api/scan` -> CLI `-Scan` JSON.
- `POST /api/scan/delete` body `{folder}` -> deletes `<AddOns>\<folder>` ONLY if it is not owned by any record and the name has no path separators; `{ok}`.

## Expansion E1

Rollback / version history: keep the zip of the version an addon was just replaced with, so it can be restored offline.

`addons.json` record: two new OPTIONAL fields, same absence-tolerant contract as the base fields - `previousFileId` (int64|null), `previousVersion` (string|null). `New-AddonRecord`/`Initialize-AddonRecordFields` default both to null; every record always carries both keys once touched by this build.

CLI (`addon-sync.ps1`):
- `Save-BackupZip -ZipPath -ProjectId -FileId -BackupsRoot [-PreviousFileId]`: called from `Sync-SingleAddon` immediately after every successful install/update, right after the record is mutated. MOVES (not copies) the just-downloaded zip from staging into `ROOT\backups\<ProjectId>\<FileId>.zip`, then deletes every other `*.zip` in that project's backup folder except the one just archived and (when given) `<PreviousFileId>.zip` - so a project's backup folder never holds more than 2 zips, and pruning is exact (by fileId, not "newest by mtime"). Best-effort: any failure is logged and swallowed, never fails the install.
- `Sync-SingleAddon`: immediately before overwriting `$Record.fileId`/`$Record.version` on an UPDATE (not a fresh install - `$isNewInstall` false), copies the about-to-be-replaced fileId/version into `$Record.previousFileId`/`$Record.previousVersion`. Takes a new mandatory `-BackupsPath` param, forwarded from `$script:BackupsPath` (`ROOT\backups`).
- `Invoke-RollbackForRecord -Record -AddonsPath -StagingPath -BackupsRoot [-DryRun]`: the `-Rollback` worker. Failed (no network) when `Record.previousFileId` is null, or when `backups\<projectId>\<previousFileId>.zip` is missing. Otherwise reinstalls via the same `Install-AddonPackage` path used by a normal sync (no download), then SWAPS fileId<->previousFileId and version<->previousVersion (so a second rollback undoes the first) and sets `pinnedFileId` = the restored fileId. Status `Rolled-back`. `-DryRun` makes no disk writes at all: it only validates and returns `Would-update` (matching the rest of the script's DryRun contract), with the row's `FileId`/`Version` naming the file that WOULD be restored.
- New param `-Rollback <int[]>`: for each id, looks up the record and calls `Invoke-RollbackForRecord`; a project id not present in `addons.json` reports `Skipped`. No network access ever (not even to validate - everything comes from the local record + local zip). Processed after `-AddonsPath` is resolved/validated and after the staging directory is (re)created, alongside the `-Unpin`/`-Ignore`/`-Unignore` block. A rollback-only run (no `-Add`/`-Only`) does not also trigger a full sync (`$hasRollback` joins `$hasRemove`/`$hasFlagsOnly` in the toSync-skip guard). `-Json` action label is `"rollback"` when `-Rollback` is present (and not a `-DryRun` run, which always reports action `"check"` per the existing convention, with `Would-update` rows). Exit codes unchanged.

Server (`addon-server.ps1`):
- Job kind `rollback` `{projectId:int}` -> `-Rollback id -Json`, mapped in `Build-CliArgs` alongside the other kinds; added to `Handle-JobsPost`'s `$validKinds` and its `projectId`-required validation (same pattern as `remove`/`install`).
- `Apply-JobCompletionSideEffects`: a completed `rollback` job (action `"rollback"`) clears any stale `updateAvailable` entry for that project when its row status is `Rolled-back` - joins the existing `sync`/`add`/`remove` branch (which already does this for `Updated`/`Installed`/`Pinned`), since a rollback pins the addon exactly like an explicit pin.
- `/api/state`: `previousFileId`/`previousVersion` reach the response automatically - `Handle-State` already clones every property present on the raw record (`foreach ($p in $r.PSObject.Properties)`), so no server code needed touching once the CLI starts writing these two fields.

## Expansion E3

Dependencies: parses each installed folder's primary .toc for declared dependencies at install/update time, and computes which are missing from the AddOns folder live (never stored).

`addons.json` record: two new OPTIONAL fields, same absence-tolerant contract as the base fields - `requiredDeps` (string[]), `optionalDeps` (string[]). `New-AddonRecord`/`Initialize-AddonRecordFields` default both to `@()`; every record always carries both keys once touched by this build.

CLI (`addon-sync.ps1`):
- `Split-TocDepList -Value`: splits one tag's value into names - comma-separated wins whenever the line has any comma, else whitespace-separated; blank pieces dropped; tolerates `$null`/empty.
- `Get-TocDependencies -AddonsPath -FolderName`: reads one folder's primary .toc (same "basename matches the folder name, else first .toc found" rule as `Get-FolderTocInfo`/`Get-TocTitle`) for `## Dependencies:` / `## RequiredDeps:` (synonyms, both feed `required`) and `## OptionalDeps:` (feeds `optional`), tag names matched case-insensitively. Returns `{required; optional}` (List[object] properties); empty lists, never throws, when the folder/.toc is missing, unreadable, or has no matching tag.
- `Get-PackageDependencies -AddonsPath -Folders`: unions required/optional across every folder of a package (each may declare its own deps), excludes any name matching one of the package's OWN folders case-insensitively (not an external dependency), dedupes case-insensitively (first-seen casing wins). Returns `{required; optional}` as plain string arrays.
- `Get-AddonsFolderSet -Path`: case-insensitive `HashSet[string]` of every top-level AddOns folder name (lowercased); empty (never throws) when `Path` is unresolvable/missing. Returned via `Write-Output -NoEnumerate` - a bare `return` on an EMPTY `HashSet` enumerates to zero pipeline objects and the caller receives `$null` instead of the set (same hazard class as the documented `List[object]`/`@()` quirk, generalized to any `IEnumerable` return - hit and fixed during this build's own offline verification).
- `Get-MissingDeps -DepNames -PresentFolders`: entries of `DepNames` not present (case-insensitively) in `PresentFolders`; also returned via `-NoEnumerate`.
- `Sync-SingleAddon`: immediately after a successful install/update (fresh installs and updates alike, alongside the other post-install record field assignments), calls `Get-PackageDependencies` over the newly installed folders and overwrites `$Record.requiredDeps`/`optionalDeps` outright - not merged with the prior value, since a new version's dependency list replaces the old one.
- `Invoke-RollbackForRecord`: the same recomputation, immediately after the restored folders are set on the record, since the rolled-back package's declared deps can differ from the version it replaces.
- `-Status` (`-Json` and the console table): resolves the AddOns path the same way a sync would, but degrades to "every requiredDep counts as missing" rather than exiting 2 when it can't be resolved or doesn't exist - `-Status` has never required a valid AddOns path and keeps that contract. Builds the present-folder set once, then adds two live-computed fields to every addon - `missingDeps` (from `requiredDeps`) and `missingOptionalDeps` (from `optionalDeps`) - never stored back to `addons.json`. `-Json`'s documented `addons[]` shape gains only these two additive fields; the console table gains a `MissingDeps` column.

Server (`addon-server.ps1`):
- `Get-PresentAddonFolders` / `Get-MissingDeps`: mirror the CLI's versions (this script is always launched standalone, never dot-sources the CLI - same duplication already used for `Resolve-EffectiveAddonsPath`/`Resolve-AddonsPath`). Same `-NoEnumerate` requirement.
- `Handle-State` (`/api/state`): computes the present-folder set once per call (shared across every record), adds `missingDeps`/`missingOptionalDeps` to each cloned addon the same way `updateAvailable` is added; `requiredDeps`/`optionalDeps` themselves reach the response for free via the existing generic per-record property clone once the CLI starts writing them (same free ride documented for E1's `previousFileId`/`previousVersion`).
- `Handle-Open`'s `what` switch gains `'url'`: body `{what:'url', url}`; 400 when `url` is missing or does not start with `https://www.curseforge.com/` or `https://addons.wago.io/` (case-insensitive prefix match); otherwise opens it via `Open-InBrowser`. No other new API surface.

The E7 "Missing deps" filter chip (already wired to `addon.missingDeps` in anticipation of this expansion) now has real data.

- Job kind `import` is a MULTI-PHASE job - 0 to several sequential `addon-sync.ps1 -Json` invocations - unlike every other kind's exactly-one-CLI-call shape:
  - `Build-ImportPlan -ImportAddons -ExistingById` (pure function, no I/O, no network) computes the phase list against the CURRENT `addons.json` (read once via `Get-AddonRecords` into a `projectId(int64) -> record` hashtable): one `-Add <comma-joined ids>` phase covering every imported projectId not already present, in one invocation (per roadmap, "one CLI invocation with all ids" - the same comma-joined-single-token requirement `Build-CliArgs`'s `sync` case already documents, since `addon-sync.ps1` is always launched as a brand-new `-File` child process here); one `-Only <id> -FileId <pinnedFileId>` phase PER addon carrying a non-null `pinnedFileId` (new-this-import or already-tracked alike - `-FileId` only ever targets a single id, so a newly-added-and-pinned addon gets two phases: the plain `-Add` installs its newest file first, then its own pin phase reinstalls the pinned one); one trailing batched `-Ignore <comma-joined ids>` phase covering every imported addon with `ignoreUpdates:true` (new or already-tracked). An imported addon already present with neither a pin nor an ignore flag needs no phase at all - `Build-ImportPlan` returns it as a pre-built `Skipped` result row instead (`{status,name,version,projectId,fileId}`, values straight from the EXISTING record, matching the shape `-Add`'s own "already present" path already produces).
  - `Start-ImportJob -JobId -StartedAt -Params` (called from `Start-Job` via a 3-line kind-gated dispatch inserted right after the existing launch-without-updateFirst special case, before the single-CLI-invocation kinds below it - which are otherwise completely untouched) builds the plan and either finishes the job immediately (`state:"done"`, zero CLI processes, `Apply-JobCompletionSideEffects` still runs so `state.json` picks it up) when there are no phases, or records the plan on the job (`Phases`, a `List[object]` of CliArgs lists; `PhaseIndex`, -1 before the first phase starts) and launches the first one, leaving the job `running`.
  - `Start-ImportPhase -Job` launches one phase's hidden `addon-sync.ps1 -Json` process exactly like the single-phase kinds do (`$Job.Process`/`OutFile`/`ErrFile`), naming its capture files `<jobId>-<phaseIndex>.out`/`.err`; increments `$Job.PhaseIndex` first.

A single failed phase (non-zero exit or unparseable `-Json` output) fails the ENTIRE job outright with an error naming which phase failed (`"Import phase N of M failed: ..."`) - later phases are never attempted, the same all-or-nothing failure shape every other job kind already has.

### Identity model (the one deliberate simplification from the roadmap's literal wording)

A Wago-sourced record has no numeric CurseForge project id, so `addons.json`'s `projectId` field stays `$null` for one; its stable identity is `slug` instead (whatever the user/CLI caller supplied when adding it - a real Wago slug, or a Wago numeric id used verbatim in the slug's URL position, per the roadmap's own "if given an id, use /addons/{id}" note - no separate resolution step exists or is needed). Every CLI target parameter, every server job/route, and every UI action that used to take a bare CurseForge `projectId` now takes a **target/key** that is either that same numeric id (CurseForge, unchanged in every way) or the string `"wago:<slug-or-id>"` (Wago) - this is the one substantive design decision this build made beyond the roadmap's own text, and it is what let the CurseForge code paths stay untouched everywhere except a dispatch point at the very top of each. `wagoId` (a record field, always toc-derived - see below) is informational only and never used for identity/routing anywhere; `slug` is.

### addon-server.ps1

- `GET /api/wago/search?q=&categoryId=&sort=&page=` -> `{items:[{slug,name,thumbnail}], page, lastPage, total}` (items parsed from HTML card snippets per the verified facts - no `wagoId`/`summary`/`author` at this level, only what a search-result card actually carries). **Verified live: Wago's site only recognises `sort=name`.** Sending any other `sort` value (`popular`/`downloads`/`recent`/`newest`/`likes`/`trending`/`latest`/`top`) makes Wago silently ignore the `search` term and return the plain popularity listing (`total` 1000), and `sort=updated` returns an empty list outright; omitting `sort` entirely is what gives correctly-ordered relevance/popularity search results. So the handler passes `sort=name` through verbatim and omits the parameter for every other value (`popular`/`relevance`/empty/unrecognised all map to "no sort param"); `GET /api/wago/categories` -> `{data:[...]}` (from the same search page's `props.allCategories`); `GET /api/wago/addons/{slug}` -> `{addon, description, metadata}`; `GET /api/wago/addons/{slug}/releases?page=` -> `{data: <releases paginator>}`; `GET /api/wago/addons/{slug}/gallery` -> `{gallery: <props, shape unverified>}`; `GET /api/wago/resolve?url=` -> `{slug}` (pure string parsing - a Wago addon's identity already IS its slug, unlike CurseForge's resolve, which needs a real search call to turn a slug into a numeric id). All keyless (no `NoKey`/409 concept - Wago never needs a key), 5-minute in-memory response cache (`$Script:WagoCache`, same size-gated eviction shape as `$Script:CfCache`, kept as a separate hashtable/function pair rather than shared). `$Script:WagoInertiaVersion` is cached in-process and additionally persisted to/reloaded from `state.json` (`Save-CheckState`/`Load-CheckState` gained a `wagoInertiaVersion` field) per SPEC's "cache the version in state.json" instruction - this server, unlike the per-run CLI, stays up for a long time and would otherwise pay the plain-HTML handshake on every single Wago request after a restart.
- Job kinds `add`/`install` accept `{source:'wago', slug, fileId?}` for a **brand-new** Wago add/install (no existing record yet to derive a key from, matching SPEC's documented body) - `Start-Job` normalizes this to `Params.projectId = 'wago:' + Params.slug` (via `Add-Member -Force -PassThru`) **before** `Build-CliArgs` ever runs, so `Build-CliArgs`'s `'add'`/`'install'` cases need **zero** changes (they already just `[string]`-cast `Params.projectId`/`fileId` generically, even before E12). An add/install targeting an **already-tracked** Wago addon (Update now / Versions-tab Install/Pin) instead sends `projectId` directly as that same `"wago:<slug>"` key, needing no normalization at all - this is the deliberate simplification from the roadmap's more elaborate always-`{source,slug}` shape (documented in the identity-model note above): `remove`/`rollback` needed **zero** server changes for Wago targets, since their `Build-CliArgs` cases and `Handle-JobsPost` validations were already generic string/truthy checks. `Handle-JobsPost`'s `'add'`/`'install'` validation accepts either `projectId` or `(source && slug)`.
- `updateAvailable` keying generalized: `Get-UpdateAvailableKeyForRecord`/`Get-UpdateAvailableKeyForRow` return `[string]projectId` when present, else `'wago:' + slug` (from a record) / `'wago:' + wagoSlug` (from a job result row) - used by `Handle-State`'s per-addon lookup and both branches of `Apply-JobCompletionSideEffects` (the check-job "record as Would-update" branch and the sync/add/remove/rollback/import/switch-source "clear a stale entry" branch, which gained `'switch-source'` to its action list at the same time). Every CurseForge record's key is unchanged in every way (same string, same map entries) - this is purely additive for Wago rows, which previously had no working key at all (`[string]$null` = `""`, a collision risk).
- New multi-phase job kind `switch-source` ("Also on Wago/CurseForge - reinstall from there", mirroring `import`'s already-established multi-phase machinery almost exactly, but as its own dedicated `Start-SwitchSourceJob`/`Start-SwitchSourcePhase`/`Complete-SwitchSourcePhase` trio rather than generalizing `import`'s - a switch is always exactly two phases, known up front, with no per-addon plan-building step `import`'s `Build-ImportPlan` needs): `{projectId (current key), toSource:'wago'|'curseforge', toTarget (numeric CF id, or a bare Wago slug/id - no "wago:" prefix, the server adds it)}` -> phase 0 `-Remove <projectId>`, phase 1 `-Add <toSource=='wago' ? 'wago:'+toTarget : toTarget>`. Dispatched from `Start-Job`/`Update-JobStatus` the same way `import` is (a 3-line/2-line kind-gated check ahead of the single-phase kinds, which are completely untouched). `Handle-JobsPost` validates all three fields present; `'switch-source'` added to `$validKinds`.
- `/api/state` exposes `source`/`wagoId`/`slug`/`curseId` per record for free, via the existing generic per-record property clone (same free ride E1/E3 already documented for `previousFileId`/`requiredDeps`) - no server code changed to add this.
- No new `/api/open` target needed for "Open on Wago": the UI reuses E3's existing `'url'` target (already allowlists the `https://addons.wago.io/` prefix).

## Expansion E19b - native host theme sync + CurseForge-tab routing (page -> host postMessage; round 12)

Round 12 shipped the SERVER + UI half of two page<->host contracts that ship alongside E19's native host (`host\FurphyHost.cs`). The WebView2/window-chrome/`DwmSetWindowAttribute` half - recoloring the tab bar/toolbar/title bar and receiving these messages via `CoreWebView2.WebMessageReceived` - is the native host's own responsibility and is documented in its own code, not here; this section covers only what `addon-server.ps1`/`ui\` own.

- Server `'cf-window'` `/api/open` target (previously UI-only since Round 9 - the button already posted it, but this server had no case for it, so every click toasted "unknown what: cf-window"; see CHANGELOG Round 9's UI entry): `POST /api/open {what:'cf-window', url}` -> 400 if `url` is missing or does not start with `https://www.curseforge.com/` (narrower than the `'url'` target from E3, which also allows `addons.wago.io`); else opens a chromeless side window (`msedge.exe --app=<url> --window-size=1100,900`, same `msedge.exe` path + `Test-Path`/`Start-Process` fallback `Open-InBrowser` already uses elsewhere in this file - there is no registry/App Paths lookup anywhere in this codebase, confirmed by grep across `addon-server.ps1`, `Addon Manager.vbs` and `curseforge-handler.vbs`); `{ok:true}`. - `settings.json` gains an optional `hostTheme` object, round-tripped the same way E19's existing `hostWindow` already is (see the E19 comments in `addon-server.ps1`'s `Get-DefaultSettings`/`Get-Settings`/`Get-SettingsView`): `{ "name": "lofi", "colors": { "bg0": "#0f1226", "bg1": "#161b34", "bg2": "#1e2445", "bg3": "#262d55", "border": "#343b66", "text": "#f2eee6", "muted": "#b3b1c9", "accent": "#ffb86b" } }`. Unlike `hostWindow` (an opaque host-owned blob this server never inspects), `PUT /api/settings`'s `hostTheme` IS validated (`Test-HostTheme`): `name` a 1-32 char string matching `^[a-z0-9-]+$` (case-sensitive - `-cnotmatch`, not PowerShell's default case-insensitive `-notmatch`, which would otherwise silently accept e.g. `"LofiNight"`), `colors` an object with at most 12 keys whose values all match `^#[0-9a-fA-F]{6}$`; anything else -> 400 `{error}` and nothing from that PUT is saved, not even its other fields (same all-or-nothing shape `releaseType`'s own out-of-range check already uses). `GET /api/settings` and `/api/state`'s `settings` both return it unmasked (not a secret) as `hostTheme`. ## Expansion E23 - CurseForge API key removed entirely (round 16)

**DECISION (2026-09-04, at Eric's explicit request), quoted verbatim: "and i want the curse api key cleared, i want that removed as a feature."** This is a deliberate DELETION of a whole feature, not a demotion - UX-SPEC.md section 1's "demote, don't delete" rule does not apply here, because the product owner asked for the capability itself to go. It is coherent now because nothing in this app has needed a key for a while: installs/updates never did (the base build's website file endpoints, section "CurseForge access facts" above), search moved to Wago + the embedded CurseForge website (E21), and drawer descriptions/changelogs/logos/screenshots come from E16's keyless enrichment chain (Wago match / addon-radar / catalogue-only) - the key only ever added a strictly richer layer on top of paths that already worked without it. **What is gone, completely - no dead code, no orphaned DOM ids, no unreachable branches, no lingering settings field:**
