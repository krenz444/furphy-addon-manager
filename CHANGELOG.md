# Furphy Addon Manager - changelog

## Round 1

No code changes applied. All three findings against addon-server.ps1 were verified and rejected:

- **StreamReader leak in Update-JobStatus (high)** - rejected. The reader is created from the already-open `$fs` FileStream and never gets its own OS handle; the enclosing `finally { $fs.Close() }` (line ~646) closes the real underlying file handle on every poll regardless of whether `$reader` was explicitly closed. There is no handle growth across repeated 800ms polls; the "~100 polls / 82s -> handle exhaustion" scenario does not occur.
- **Addon disable/enable (medium)** - rejected, out of scope for this round. Not present anywhere in SPEC.md (the authoritative spec): no `disable`/`enable` job kind, no `disabledAt`/`disabledReason` fields in the addons.json record contract, no `-Disable`/`-Enable` CLI params. The "E11 bulk actions" reference traces to ROADMAP.md ("E11 - Bulk actions"), a future-work doc, not the current spec. Implementing it now would require unauthorized changes to addon-sync.ps1 (a different component) and to the addons.json record shape.
- **Download progress percentage (medium)** - rejected, out of scope for this round. SPEC.md's JobStatus shape (`id, kind, params, state, startedAt, finishedAt, exitCode, log[], results[], error`) and result-row shape (`status, name, version, projectId, fileId`) have no progress field, and the job panel spec only calls for live log lines plus a final results list - which addon-server.ps1 already provides via the sync.log tail in `Update-JobStatus`. The fix also requires CLI-side changes (parsing CurseForge response headers in addon-sync.ps1), a different component than the one being fixed here.

### cli component (addon-sync.ps1)

- **Fixed (high)** - a `-DryRun -Json` "Would-update" row paired the NEW target `version` string with the OLD (currently-installed) `fileId`. In the main sync loop, every results row was built as `FileId = $record.fileId` unconditionally; for a real Installed/Updated row this is correct because `Sync-SingleAddon` mutates `$Record.fileId` in place before returning, but its DryRun branch returns early without ever touching `$Record`, so `$record.fileId` there still held the old/currently-installed id while `Version` (from the newly selected file's `displayName`) already reported the new/target version - reproduced directly: project 911525 recorded at fileId 8672833/v9.1 with 8787143/v9.2 actually newest, `-DryRun -Json` returned `{"status":"Would-update","version":"v9.2","fileId":8672833}`, an impossible pairing (8672833 is v9.1). This corrupted `addon-server.ps1`'s persisted `updateAvailable` map (and `/api/state`/`state.json`) the same way, so any explicit-fileId install action built on it would silently re-pin the addon to the file it is already on instead of the real update. Fixed by having `Sync-SingleAddon`'s DryRun branch return an explicit `FileId = $selectedFileId` (the newly selected/target file, matching `Version`) and having the outer loop prefer that field when present, falling back to `$record.fileId` for every other status (which has no such field, since only DryRun leaves `$record` unmutated).
- **Fixed (medium)** - `-Files <id> -Json` added an undocumented `error` field to its JSON output on a network failure (`{action,projectId,files,error}`), but SPEC.md line 55 documents the shape as exactly `{"action":"files","projectId":N,"files":[...]}`, and no other `-Json` action in the script adds an ad-hoc field like this. Removed the `Add-Member ... 'error'` block; the failure is still logged to sync.log (unchanged) and the non-JSON table path still prints `ERROR: $filesError` to the console.
- **Fixed (high)** - every array-typed CLI parameter (`-Add`, `-Remove`, `-Only`, `-Unpin`, `-Ignore`, `-Unignore`) silently mis-bound under the script's real invocation (`powershell.exe -File addon-sync.ps1 ...`, used by both the launcher and `addon-server.ps1`'s job dispatch): a comma-joined token like `-Remove 1521253,911525` (quoted or not) arrived as one literal-comma string instead of being split, so `-Remove` silently no-opped (reported `Skipped`, removed nothing) and `-Add` (declared `[int[]]`) made PowerShell's own parameter binding throw before the script body ever ran - exit code 1, a native `Cannot convert value ... to type System.Int32[]` error on stderr, and zero stdout even with `-Json`. Declared all six parameters `[string[]]` and added `ConvertTo-ExpandedStringArray`/`ConvertTo-ExpandedIdArray`, called immediately before the existing "compute targeting flags" block, which re-split every raw element on commas and (for the five id-typed params) parse each piece to `int64`; a non-numeric piece now fails through the script's normal `Write-Log`/exit-2 path instead of throwing past it. Verified end-to-end via `-File`: `-Remove 1521253,911525 -Json` now correctly empties `addons[]` in one call (previously a `Skipped` no-op); `-Add 1521253,911525 -FileId <id>` now correctly parses two ids and hits the existing "-FileId requires exactly one project id" validation (previously crashed at parameter binding, before reaching that check); comma-joined `-Ignore`/`-Unignore`/`-Unpin` verified likewise; single-value (no-comma) usage of all six parameters regression-tested unchanged.

### server component (addon-server.ps1) - unquoted Handle-Open paths

All five findings verified against the code and fixed. `Start-Process -ArgumentList` joins array/string elements with spaces and never quotes them (the same pitfall already documented and handled for `New-CliProcessArgs`), so every path handed to `notepad.exe`/`explorer.exe` in `Handle-Open` needed the same `'"' + $path + '"'` treatment - most visibly for the production deploy target `C:\Program Files (x86)\World of Warcraft\_retail_\AddonSync\`, whose ROOT and derived paths (sync.log, addons.json, last-run.txt, backups\) all contain spaces and parentheses, and for the AddOns folder itself (`...\World of Warcraft\_retail_\Interface\AddOns`).

- **Fixed (high)** - `'folder'` case (line ~1557): quoted `$addonsPath` before passing to `explorer.exe`.
- **Fixed (high)** - `'addons'` case (line ~1565): quoted `$Script:AddonsJsonPath` before passing to `notepad.exe`.

### server component (addon-server.ps1) - multi-id sync job silently dropped ids

- **Fixed (high)** - `Build-CliArgs`'s `sync` job kind built a multi-id sync as `-Only id1 id2 id3 ...`, with each id its own separate `-ArgumentList` element passed into `Start-Process`. addon-sync.ps1 is always launched as a brand-new `powershell.exe -File ...` child process (never in-process), and Windows PowerShell 5.1's own `-File` argument binder does not collect several space-separated bare tokens into one array-typed parameter the way an in-process call (`& $script -Only 1 2 3`) does - reproduced directly: only the first id bound to `-Only`, and every id after it fell through as a positional value for whichever parameter came next, with no error surfaced anywhere (not in the job's results, not in sync.log, not in server.log). A multi-id sync job would therefore silently sync/reinstall only the first addon in the requested batch. This pairs with the cli component's fix this same round: addon-sync.ps1's id-array parameters are `[string[]]` and re-split any comma-joined token internally (`ConvertTo-ExpandedStringArray`/`ConvertTo-ExpandedIdArray`), and a single comma-joined token like `"1521253,911525"` (unlike separate space-separated tokens) does survive `-File` binding intact as one literal string - verified directly against that real normalization code. Changed the `sync` case to comma-join `$Params.ids` into one `-Only` token instead of adding each id as its own array element; `install`/`add`/`remove` were already single-id and needed no change. Not reachable through any UI control built so far (My Addons only ever sends single-id sync jobs; the multi-id "Update selected" bulk action is still on the E11 backlog), so it had produced no visible failures yet, but would have silently corrupted multi-id sync results the moment that UI ships.

### cli component (addon-sync.ps1)

- **Fixed (high)** - author backfill for the pre-existing "Unknown author" records. `Sync-SingleAddon`'s `Up-to-date` early return (the path hit for every already-current addon) never touched `$Record` at all, so the ~37 records saved before the `author` field existed stayed `null` forever - a plain sync never has a reason to revisit a file it isn't installing. - **Rejected** - "spurious backtick before colon" on `"$key`: $($counts[$key])"` (medium). - **Fixed (high)** - `Invoke-RollbackForRecord`'s success path swapped `fileId`/`version`/`previousFileId`/`previousVersion` and set `pinnedFileId`, but never touched `Record.fileName`, leaving it naming the file that was just replaced rather than the one actually restored (reproduced live: rolling project 911525 back from fileId 8787143/v9.2 to fileId 8672833/v9.1 left `addons.json` with `fileId 8672833` / `version "v9.1"` but `fileName` still `"Max_Camera_Distance-v9.2.zip"`, confirmed via both `/api/state` and `-Status -Json`). Verified offline against a hand-built backups folder (no CurseForge access): a rollback with its sidecar present now restores the correct `fileName` alongside `fileId`/`version`; a rollback whose backup predates the sidecar leaves `fileName` unchanged and still reports `Rolled-back` with no crash; `Save-BackupZip` unit-verified to write the sidecar, prune an unrelated stale zip+sidecar pair, and keep exactly the two zip+sidecar pairs that matter (current + previous) after a second archive.

### E1 - Rollback / version history (addon-sync.ps1 / addon-server.ps1 / ui)

- **Added** - `addons.json` records gain `previousFileId`/`previousVersion` (both null until an addon has been updated at least once), backfilled on load like `author`/`ignoreUpdates`/`pinnedFileId`/`releaseType` before them so an old record never trips a missing-property dot-assignment.
- **Added** - every successful install/update in `Sync-SingleAddon` now records what it replaced (`previousFileId`/`previousVersion`, set right before the record's `fileId`/`version` are overwritten - only on an actual update, not a fresh install) and archives the just-downloaded zip into `ROOT\backups\<projectId>\<fileId>.zip` via new function `Save-BackupZip`, which moves the file out of staging (not a copy - staging is wiped at end of run) and immediately prunes that project's backup folder down to at most 2 zips (the one just archived plus, when known, `previousFileId`'s), by exact fileId match rather than file age. Archiving is best-effort and never fails an otherwise-successful install.
- **Added** - new CLI param `-Rollback <id[]>` and worker function `Invoke-RollbackForRecord`: reinstalls a project from its locally archived previous-version zip (same `Install-AddonPackage` path as a normal install, zero network access), swaps fileId/version with previousFileId/previousVersion (so a second rollback undoes the first), and pins the restored fileId so a following plain sync does not immediately update it away again. Reports `Rolled-back` on success, `Failed` (with the reason logged to sync.log) when there is no recorded previous version or its backup zip is missing, `Skipped` for an unrecognized project id. `-DryRun -Rollback` makes zero disk writes and reports `Would-update` under action `"check"`, matching every other DryRun path in the script. A rollback-only run does not also trigger a full sync of every other addon.
- **Added** - `addon-server.ps1` job kind `rollback` `{projectId}` -> `-Rollback id -Json`, wired into `Build-CliArgs`/`Handle-JobsPost` alongside the existing kinds; `Apply-JobCompletionSideEffects` clears the `updateAvailable` entry for a project on a successful `Rolled-back` row, same as it already does for `Updated`/`Installed`/`Pinned`. `previousFileId`/`previousVersion` reach `/api/state` for free through `Handle-State`'s existing generic per-record property clone - no server-side field mapping needed.
- **Added** - UI: a "Roll back to `<version>`" entry in the My Addons kebab menu (only rendered when `addon.previousFileId` is set - pushed conditionally rather than ternary'd, since a `null` array entry renders as a visible menu separator, not nothing), a muted "Previous" tag on the matching row in the drawer's Versions tab, and a tooltip ("Rolled back — unpin to resume updates.") on the Pinned chip when the pin resulted from a rollback (`pinnedFileId === previousFileId`).
